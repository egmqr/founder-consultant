title: Replicas and multiple regions can show users stale or overwritten data
areas: [DATA]
checks: [DATA-9]
---
**Summary.** Once reads come from replicas, a user's own write may not be visible on the next read because the replica lags; the app looks broken. Route a user's reads to the primary for a short window after they write. Monitor replica lag and send reads to the primary when it crosses a threshold (lag spikes under load, big transactions and schema changes). When two places can accept writes to the same record, choose a conflict rule on purpose (version checks that reject stale updates, or a merge), so one change isn't silently dropped. The same applies to offline-first clients and caches that sync later.

**Takeaways**
- Read-after-write consistency for the writing user
- Replica lag is monitored with a threshold that reroutes reads
- Concurrent writes use an explicit conflict rule (version check or merge), never a silent overwrite
