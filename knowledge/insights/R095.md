title: Breaking API changes go to a new version that runs beside the old one until a dated sunset
areas: [CHG]
checks: [CHG-6]
---
**Summary.** Patching a public API one endpoint at a time, each time a customer asks for something, slowly turns it into an inconsistent set of workarounds that clients can't predict and docs can't follow. The signal to version is not feature count but a fix you can't make without breaking someone: renaming a field, reshaping a response, changing auth, removing a mistake. The new version runs beside the old one behind the same domain with shared authentication; new clients start on it, existing clients get a dated migration window, and every old-version response says when it ends and where to go.

**Takeaways**
- List every change you'd make to the API if compatibility didn't matter; that list is the next version's scope
- A new version is a parallel path with its own routes, not a rewrite that replaces the old one on launch day
- Every old-version response carries a deprecation and sunset date plus a link to the migration guide
- An API with no sunset policy means maintaining every version forever
- AI-added endpoints need a contract check against existing clients before they ship
