title: When a provider retires a service, compliance coverage and code coupling both move
areas: [VEN]
checks: [VEN-7]
---
**Summary.** Cloud providers retire or replace services, and the replacement is often a different runtime and API rather than an automatic upgrade. Two things break at once: code written directly against the old service's SDK becomes migration work, and compliance agreements (such as health-data or data-processing agreements) that cover services by name may not cover the replacement. A retired service usually keeps running for a while but stops getting features, so the time to plan the move is when the retirement is announced.

**Takeaways**
- Business logic talks to provider frameworks through an internal interface, so the provider service can be swapped
- Keep a list of every provider service that touches regulated data, and recheck it against the current compliance agreement whenever a service changes
- Track each provider service's lifecycle status; an announced retirement gets a dated migration plan, not an emergency later
