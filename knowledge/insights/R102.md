title: Don't wrap a command-line tool in a protocol server the agent doesn't need
areas: [HAR]
checks: [HAR-15]
---
**Summary.** Wrapping a tool that already has a command-line interface in a tool-protocol server adds schema, transport and permission overhead to every call, and often exposes fewer options than the command itself. An agent that can run the command directly gets the answer in one call with less latency and fewer tokens. Protocol servers earn their place for services with no command line, sign-in negotiation, or multi-step stateful work. At hundreds of tool calls per session, the per-call overhead adds up.

**Takeaways**
- List every tool-protocol server and flag the ones that wrap a tool with an existing command line
- Measure latency and token cost per call against the direct command for the most-used tools
- Keep protocol servers where they add something: no command line, auth negotiation or state across steps
